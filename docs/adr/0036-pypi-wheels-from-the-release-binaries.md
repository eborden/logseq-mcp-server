# Publish the release binaries to PyPI as platform wheels built from the GitHub Release

## Context

[ADR-0035 (native-binary-release-on-github-releases)](0035-native-binary-release-on-github-releases.md) ships the Rust server as native binaries on GitHub Releases, started by a shell launcher inside the Claude Code plugin. It gives up the one-line install that MCP clients outside Claude Code expect, and says an npm channel is the maintainer's later choice (Decision 8). The facts that matter for a second channel:

- **Clients start servers with `uvx` or `npx`.** A copy-paste config (`"command": "uvx", "args": ["logseq-mcp-server"]`) is how most MCP hosts that are not Claude Code are set up. Nothing in the first release serves them except a clone and a build, or a hand-downloaded binary.
- **The PyPI name is free.** On 2026-10-09 `https://pypi.org/pypi/logseq-mcp-server/json` answers 404. The npm name of the same spelling belongs to another maintainer (ADR-0035), so PyPI is the one registry where the project can hold its own unscoped name. Other LogSeq MCP servers exist on PyPI under other names, so the name is not a differentiator. PyPI has no scopes, so a name is first come, first served, and it is held only by publishing a real release: PyPI discourages empty placeholder projects.
- **PyPI can carry a native binary.** A wheel is a zip with a platform tag. Anything in its `scripts` data directory is installed as an executable on `PATH` by pip, uv and pipx, and an installer rewrites a script's shebang only when the file starts with `#!python`, so a binary is copied untouched. `uvx logseq-mcp-server` runs the Rust binary itself, with no Python process beside it. Projects such as ruff ship this way.
- **The bytes must be the ones that were gated.** `release.yml` (ADR-0035) builds each target, runs the parity test and the unit tests against that build, writes `SHA256SUMS` and attests build provenance. A second build for PyPI would produce different bytes that no gate saw, and a wheel built outside that run would sit outside its attestation.
- **Nothing is published from a session.** ADR-0017's rule, carried by ADR-0035 Decision 10 and CLAUDE.md: publishing is a manual workflow, run by the maintainer, from `main`, with `dry_run` on by default and third-party actions pinned by commit SHA.
- **A release job should install nothing.** A build step that runs `npm ci` or `pip install` before it handles the bytes that ship adds a supply chain to the one place that must have none (Foundations 4.11).

## Decision

We publish the three binaries of ADR-0035 to PyPI as platform wheels. **The wheels are built in the release run, from the gated binaries, and ride on the GitHub Release. A second manual workflow uploads exactly those files to PyPI.** A session builds, uploads or publishes nothing.

1. **One project, wheels only.** The PyPI project is `logseq-mcp-server`, owned by the maintainer. There is no source distribution: a source build would need a Rust toolchain and would not be the gated binary. A platform with no wheel (Windows, Linux on arm64) fails to install with pip's "no matching distribution", which is the same support as ADR-0035's first release, stated in the package description.
2. **What a wheel holds.** The release binary, unmodified, at `logseq_mcp_server-<version>.data/scripts/logseq-mcp-server` with mode 0755, plus `METADATA`, `WHEEL`, `RECORD` and the two licence files (`LICENSE`, `THIRD-PARTY-NOTICES.txt`) in `.dist-info/licenses`. The Python tag is `py3-none`, since there is no Python code. The metadata is 2.4, with `License-Expression: MIT` and the long description from `pypi/README.md`. The platform tags:

   | Release target | Wheel platform tag |
   |---|---|
   | `aarch64-apple-darwin` | `macosx_11_0_arm64` |
   | `x86_64-apple-darwin` | `macosx_10_12_x86_64` |
   | `x86_64-unknown-linux-musl` | `manylinux_2_17_x86_64.musllinux_1_2_x86_64` |

   The musl binary is static (ADR-0035 Decision 1), so it runs on glibc and musl alike and takes both Linux tags. The macOS tags are Rust's default minimum versions, and **the builder holds them** (Decision 4): a macOS binary that needs a newer macOS than its tag promises is refused.
3. **The wheels are part of the release set.** This ADR extends the release set of ADR-0035 Decision 3 with the three wheels. `release.yml` gets one more job, `wheels`, which runs with the read-only token after the legs and the notices job, and builds the wheels from their files. The job then checks every wheel on its own, apart from the builder: the executable inside each of the three is the binary of the target its tag names, and the Linux one installs into a clean environment. The last job, the only one with a write token, then lists the three wheels in `SHA256SUMS` beside the binaries, the licence and the notices (eight files, so the `SHA256SUMS` has eight lines), attests them with the binaries (`actions/attest`, one subject list), and attaches them to the draft release. A dry run builds and checks them like everything else and uploads them as workflow artifacts. The launcher is unaffected: it looks up only its own file names in `SHA256SUMS`. The wheels are built at the release's commit, so the metadata and the long description are the release's, and a later change on `main` can't reach them.
4. **The builder is one standard-library Python script**, `scripts/pypi/build_wheels.py`, not a packaging tool. It needs nothing installed (the runner has `python3`), so no package is fetched in the job that handles the binaries. It refuses, and leaves no wheel behind, unless:
   - the version is plain `x.y.z`;
   - every input is a regular file (a symbolic link is refused), `SHA256SUMS` is well formed, lists it and matches the hash of the very bytes the builder then ships (each file is read once);
   - each binary is for the CPU and operating system its tag claims, read from its header: a 64-bit Mach-O executable for arm64 or for x86_64, or a 64-bit x86_64 ELF executable for System V or GNU, so a mislabeled asset can't ship;
   - a macOS binary names the macOS it needs (`LC_BUILD_VERSION` or `LC_VERSION_MIN_MACOSX`) and that is not newer than its tag (11.0 on arm64, 10.12 on Intel), so the tag is a checked fact and not a claim;
   - the output directory holds no wheels or half-written wheels already.

   The same inputs always give the same bytes (a fixed timestamp, a fixed file order). A failure while writing removes the wheels already written. Its tests are `scripts/pypi/test_build_wheels.py`, run by the `wheels` job and by the guard job.
5. **The upload workflow is `.github/workflows/pypi.yml`**, under ADR-0035 Decision 10's rules. It builds nothing and reads no version file:
   - It runs only on `workflow_dispatch`, only from `main`, and `dry_run` defaults to true. Its inputs are `version` and `dry_run`.
   - **Preflight** fails the run before it downloads anything if the version is not plain `x.y.z`, if the GitHub Release `v<version>` is not public (a draft or a pre-release), or if PyPI already has the version (a file name can never be uploaded twice).
   - **Verify** downloads the release's wheels, `SHA256SUMS` and the Linux binary. It checks that `SHA256SUMS` lists exactly three wheels and that each wheel and the binary match; verifies each wheel's attestation with `gh attestation verify` against this repository, `release.yml`, the `main` branch and the commit the release tag points at (so a wheel swapped on the release, or an older attested wheel renamed for this version, fails); installs the Linux wheel into a clean virtual environment and checks the executable is the release's Linux binary byte for byte; and uploads the wheels and their checksums as workflow artifacts. A dry run stops here.
   - **Publish** runs only on a real run and only after the other jobs. It is the only job with a token, `id-token: write`, and the only one that can upload. It checks the three wheels against their checksums again and uploads them through the pinned action with no input but the directory. It waits for the `pypi` environment, which the maintainer configures with themselves as a required reviewer, so an upload is a second deliberate click, as publishing the draft is for GitHub Releases.
6. **Trusted publishing, no stored credential.** PyPI is told to accept uploads from this repository's `pypi.yml` in the `pypi` environment, and exchanges the run's OIDC identity for a short-lived token. No API token is created, stored or referenced anywhere. The upload step is `pypa/gh-action-pypi-publish` pinned by commit SHA: PyPA's own action, the one the trusted-publishing guide names, at v1.14.2 (published 2026-07-29, commit `dc37677b2e1c63e2034f94d8a5b11f265b73ba33`). It also publishes PEP 740 attestations for the files, by its default, so the action takes no input besides the directory. This is the only new third-party action, and it is vetted here as CLAUDE.md requires.
7. **One version, one release.** The PyPI version is the release version. A wheel is never edited or re-uploaded. A bad upload is fixed by a new patch version cut the same way, and yanking the bad one on PyPI is the maintainer's call.
8. **The plugin does not change.** The Claude Code plugin keeps ADR-0035's launcher. PyPI is a channel for other MCP hosts, not a second way the plugin starts the server.
9. **The first publish is manual, by the maintainer, in this order, none of it from a session:**
   1. ADR-0035 Decision 12 runs as written. Its dry run of `release.yml` now also builds the wheels: the `wheels` job's log shows the builder's checks, including the macOS minimum, and its refusal is a failed run. Its pre-publish check (12.4) gains one step: install a wheel from the downloaded draft (`gh release download` into the empty directory, then `uvx --from <wheel file> logseq-mcp-server` through an MCP client, on a clean macOS and a clean Linux machine) and call one tool. The release is then published, and the post-publish check passes.
   2. **Hard prerequisite, before any real run of `pypi.yml`:** in the repository's settings, create the `pypi` environment with the maintainer as a required reviewer and deployment limited to `main`. GitHub creates an unprotected environment on the first run of a job that names one that doesn't exist, and then a real run uploads with no second click. Nothing in the workflow can detect that, so this step is the guard. Then, on PyPI, register a pending trusted publisher for the project `logseq-mcp-server`: owner `eborden`, repository `logseq-mcp-server`, workflow `pypi.yml`, environment `pypi`.
   3. Run `pypi.yml` with `dry_run` on and read the log: the checksums, the attestations and the install check.
   4. Run it with `dry_run` off, and approve the `pypi` environment. That uploads the files and creates the project.
   5. **Post-publish check.** On a clean macOS machine and a clean Linux machine, with no override, run `uvx logseq-mcp-server` through an MCP client and call one tool. This is also where it is confirmed that an installer's copy of the binary runs without a Gatekeeper warning. If it fails, nothing is edited: the fix is a new patch version, and the maintainer decides whether to yank the old one.
   6. A follow-up PR adds the `uvx` install to the README, the changelog and `pypi/README.md`'s links. They say nothing about PyPI until the check above passes.

### Alternatives rejected

- **Building the wheels in `pypi.yml`, after the release is public.** It would keep `release.yml` as it is, but the wheels would be built in a run that has no gate and no attestation of its own, from files downloaded from the release and a README and metadata taken from whatever `main` holds by then. Building them in the release run puts them inside the checksum, the attestation and the pre-publish check, and makes PyPI hold the files that were on the draft.
- **A pure-Python launcher wheel that downloads the binary on first run.** It keeps the wheel small and avoids per-platform wheels, but it needs the network at first start, leaves a Python process resident for the whole session (the cost ADR-0035 Decision 6 avoided by choosing a shell `exec`), repeats the launcher's download and checksum logic in a second language, and the wheel is not the gated bytes.
- **maturin or another packaging tool.** It would compile the crate again inside the job, producing bytes no gate saw, and it adds a build dependency. The binary is already built and attested, so only a zip with the right metadata is missing.
- **Triggering `pypi.yml` when the release is published.** It would remove the second manual step, but it breaks ADR-0035 Decision 10 (manual, from `main`, dry run by default) and puts a registry upload behind a click that is meant to publish a GitHub release.
- **npm first.** It reaches the same hosts, but its unscoped name is taken, it needs a scope, and an `npx` client needs Node, which this project's launcher avoids. It stays the maintainer's later choice (ADR-0035 Decision 8) and is not affected by this decision.
- **A container image.** The server must reach LogSeq's API on the host's localhost, which a container hides by default, and a client config that starts a container is heavier than one that runs a binary.

## Consequences

- **More reach for one registry's worth of work.** A client config of `uvx logseq-mcp-server` works on macOS and Linux x86_64 with no Rust toolchain, no clone and no Node. **This relaxes the consequence ADR-0035 accepted** ("no `npx` one-liner") for hosts that are not Claude Code: they get a one-liner through `uvx`. ADR-0035's other decisions stand.
- **The release set grows by three files**, and `release.yml` by one read-only job. The launcher, the plugin and the binaries are unchanged. A dry run of `release.yml` now proves the wheels as well.
- **`pypi.yml` has never run, and neither has the new part of `release.yml`**, as `release.yml` had not when ADR-0035 was accepted. The first dry runs on GitHub are the real test, and the attestation checks, `gh release download` and the trusted-publisher exchange cannot be tried before a release exists.
- **PyPI is immutable.** A file name is uploaded once. A mistake costs a version number, and the name stays taken either way.
- **The name is claimed by the first real upload.** Until then anyone could publish `logseq-mcp-server` on PyPI. The risk is accepted: a placeholder would break PyPI's guidance, and the first release is close.
- **Platform support is exactly ADR-0035's.** No Windows and no Linux arm64 wheel. Adding a target is additive: a row in the table above, the target in `release.yml`, and a matching branch in the builder's header check.
- **Licence notices ship in each wheel**, as they do on the release. The package declares `License-Expression: MIT`, the project's licence (ADR-0023). The binary also statically links crates under other licences (their texts are in `THIRD-PARTY-NOTICES.txt`), and whether the expression should name them too is the maintainer's call, to be made before the first upload. It is metadata only and changes no file in the wheel.
- **The checksum and the attestation cover the wheels and the binaries.** `LICENSE` and `THIRD-PARTY-NOTICES.txt` are listed in `SHA256SUMS` but not attested, as ADR-0035 Decision 4 already states, and the wheels carry copies of them.
- **Python is a tooling dependency of the repository now, but only `python3` itself.** The workflows use the runner's `python3` with the standard library and install no package (the one `pip install` is of a wheel just built, from the local file with no index). The guard job also needs `python3` on its runner, because a guard test runs the builder's tests (GitHub's Ubuntu runners have it, and so does a macOS developer machine).
- **A missing `pypi` environment can't be detected by the workflow.** The prerequisite in Decision 9.2 is a step the maintainer does, and the dry run of `pypi.yml` doesn't need it.

## Mechanical enforcement

- test: `tests/guards/pypi-workflow-guards.test.ts` (pypi.yml triggers only on workflow_dispatch, gates every job to main and the publish job also to a real run, defaults dry_run to true, gives only the last job a token and only id-token: write, runs it in the pypi environment, makes the upload the last step through the pinned PyPA action with no input but the directory and no command, references no secret or API token, pins every action by SHA with a version comment, builds nothing and reads no version file, and downloads exactly the wheels, SHA256SUMS and the Linux binary, checks them against SHA256SUMS, verifies each attestation against release.yml, main and the release's commit, runs the install check and re-checks the hashes before the upload, with negative tests that it fails when any of that is broken)
- test: `tests/guards/release-wheels-guards.test.ts` (release.yml builds the wheels in a read-only job that needs every leg, runs the builder and its tests, checks the installed executable and the wheel set, and installs nothing from an index; the last job lists the three wheels in SHA256SUMS, attests them with the binaries and attaches them to the draft release, with negative tests for each)
- test: `tests/guards/release-workflow-guards.test.ts` (release.yml stays manual, main-only, dry-run by default and drafts only, with exactly one write job that needs every other job including the wheels job, and no other workflow creates or edits a release or a tag, which covers pypi.yml)
- test: `tests/guards/pypi-wheels.test.ts` (the builder's own tests pass in the guard job, and the builder imports only the standard library and nothing dynamic, so the release job installs nothing)
- test: `scripts/pypi/test_build_wheels.py` (one wheel per target with the binary byte for byte and executable, a correct RECORD, the right tags and metadata, identical bytes on a second build, no wheel left after a failure, and a refusal for a wrong checksum, an unlisted, missing or symlinked file, a binary for another CPU, OS or file type, a macOS binary that needs a newer macOS than its tag or names none, a bad version and a stale output directory)
- ci: `.github/workflows/ci.yml` (the guard job runs the guards above, and actionlint and ShellCheck lint every workflow, including pypi.yml and the new job of release.yml)
- reviewer: the maintainer's dry runs of release.yml and pypi.yml prove the wheels job, the attestation checks and the install checks before the first upload (Decision 9), the `pypi` environment is created with a required reviewer before any real run of pypi.yml (Decision 9.2), and that no PR adds a step that uploads to PyPI, tags or releases outside the manual workflows
