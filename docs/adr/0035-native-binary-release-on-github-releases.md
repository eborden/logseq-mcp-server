# Release the Rust server as native binaries on GitHub Releases, started by one thin launcher

## Context

The Rust server is the only server (#349, #356). Nothing ships it yet. The pieces that were built for the TypeScript server are left over and don't run:

- `.claude-plugin/plugin.json` starts `node ${CLAUDE_PLUGIN_ROOT}/dist/index.js`, and there is no `dist/`.
- `package.json` has `bin` and `main` pointing at `dist/index.js`, a `build` script that exits 1, and `files` that list `dist`.
- `.github/workflows/publish.yml` builds the TypeScript server and runs `npm publish`.

[ADR-0017 (manual-npm-publish)](0017-manual-npm-publish.md) and [ADR-0018 (ship-as-claude-code-plugin)](0018-ship-as-claude-code-plugin.md) both say in their enforcement sections that how the Rust binary is shipped is open (#350, #355). This ADR closes that. The cutover to `main` is #354. The work that follows is #418 (the release workflow) and #419 (the launcher and the manifests), and neither starts until this ADR is accepted.

What the decision has to fit:

- **Nothing may be published, tagged or released from a session.** ADR-0017 makes publishing a manual workflow the maintainer starts. CLAUDE.md states the working rule ("never publish, tag or release from a session") and it stands for whatever replaces the npm workflow. A release is a public artifact.
- **The plugin is installed from a git checkout.** The repository is its own marketplace with `"source": "./"` (ADR-0018), so a marketplace install copies the repository into a cache. Anything the server needs that isn't in git has to arrive some other way, and nothing can assume an npm publish.
- **The npm name `logseq-mcp-server` is not ours.** On 2026-10-08 `npm view logseq-mcp-server` shows a published package, `1.0.0-beta.7`, created 2025-08-26 and maintained by someone else, from another repository. The maintainer can't publish under that name, and this ADR doesn't assume otherwise (the maintainer confirms availability and ownership of any name before anyone relies on it). `CHANGELOG.md` says only that nothing was published from this repository, which is a different claim. The hazard is already in the docs: the README, `CHANGELOG.md`, ADR-0017 and ADR-0018 present `npx -y logseq-mcp-server` as this project's install line, and today that command runs a stranger's package. The README fix is #417. Accepted ADRs aren't edited, so this ADR is where the correction is recorded for them.
- **The binary is small and has no runtime dependencies.** It is one file of about 3 to 4 MB (#304), with no TLS and no OpenSSL (`reqwest` is built without TLS; LogSeq's API is plain HTTP on localhost). The footprint is the reason for the port: about 9 ms to the first `initialize` response against about 290 ms for Node, and about 2 MB resident against about 64 MB (#304, one tool ported; the full-port numbers are #353's).
- **Four targets were built in CI in #304**, in a temporary job that was deleted afterwards, with a cold release build of about 1 to 4 minutes and about 30 to 80 seconds with a warm cache: aarch64 macOS (`macos-latest`), x86_64 macOS (`macos-15-intel`, the slowest at about 4 minutes cold), x86_64 Linux and x86_64 Windows. That job proved compile and link only. Today's `ci.yml` runs the parity and unit-test steps on the Linux glibc target only, and the toolchain file pins no extra targets, so the macOS legs and the musl leg of a gate are new and unproven.
- **Windows differs.** Where there is no `localtime_r`, "today" is the UTC day, while the retired TypeScript server read the local day on every platform (`rust/src/dates.rs`, listed in #299). The date presets of `query_by_date_range` and the prompts that name a week or a month can be a day off near midnight. No CI job runs the crate's tests on Windows.
- **macOS needs a signing story.** Developer ID signing and notarization need the maintainer's Apple account, which a session can't hold. An arm64 binary has to carry at least an ad-hoc signature to run, and the Rust linker adds one.
- **A Node launcher costs memory and a requirement.** A launcher written in JavaScript can't replace itself with the binary, so a Node process sits beside it for the whole session. Measured for this ADR with a stand-in (Node 24.13 on an Intel Mac, three runs, an idle Node process that has spawned one child with inherited stdio): about 34 to 35 MB resident, and `node -e 0` takes about 0.2 s wall on a cold start here. A POSIX `sh` launcher that ends in `exec` is replaced by the binary, so nothing of the launcher stays resident (the same stand-in measured about 0.6 MB, which is the stand-in child itself). So the server would go from about 2 MB to about 36 MB resident with a Node launcher, against about 64 MB for the retired server: roughly half, not the 97% saving the port was measured on. A Node launcher also makes Node a runtime requirement for every user, where [ADR-0022 (minimum-node-22-12)](0022-minimum-node-22-12.md) scopes Node to the dev tooling, and native Claude Code installs need no Node. Node's `fetch` doesn't read `HTTP_PROXY` or `HTTPS_PROXY`, while `curl` does. These are single local figures, not a benchmark.

Options for getting the binary to the user, weighed on the issue (#350):

1. **Per-platform binaries attached to a GitHub Release, with one thin POSIX `sh` launcher** that picks, downloads, verifies and `exec`s the right one. The plugin starts it.
2. **The same, with a Node launcher** that the plugin and an npm package share.
3. **An npm launcher package with one optional dependency per platform** (the esbuild pattern).
4. **A binary-only plugin**, with the binaries committed to git or to a release branch and a platform picker in front of them.
5. **`cargo install` only.**

## Decision

We recommend and choose option 1: **native binaries on GitHub Releases, started by one POSIX `sh` launcher in the repository that `exec`s the verified binary.** There is no npm channel in the first release. The first release is a manual step by the maintainer, and no session builds, tags, publishes or releases anything.

1. **Targets.** The first release carries three binaries:
   - `aarch64-apple-darwin`, built on `macos-latest`.
   - `x86_64-apple-darwin`, built on `macos-15-intel`.
   - `x86_64-unknown-linux-musl`, built on `ubuntu-latest`. The binary is static, so it doesn't depend on the glibc of the runner or of the user's distribution. A binary built on a current Ubuntu needs a glibc that older distributions lack. Every dependency is pure Rust, so the musl build needs no C library beyond `libc`.

   `x86_64-pc-windows-msvc` is **not in the first release**. It joins when its date behavior is settled (a local-time implementation, or the maintainer accepting UTC in a recorded decision), the gate below runs green on a Windows runner, and a Windows launcher exists (below). `aarch64-unknown-linux-musl` is also later: it wasn't measured in #304 and nobody has asked. Adding a target is additive. The launcher says plainly when a platform has no binary, and names the manual route.
2. **Builds happen in one manual workflow**, a new `.github/workflows/release.yml` (#418):
   - It runs only on `workflow_dispatch`, never on push, tag or pull request, and only from `main`. Its inputs are `version` (it must equal the version in `rust/Cargo.toml`, `package.json` and both plugin manifests, or the run fails before it builds) and `dry_run`, which defaults to true.
   - It builds each target with `cargo build --release --locked --target <triple>` on the toolchain `rust/rust-toolchain.toml` pins, with the target added. Each target is held to the same steps the release build runs in `ci.yml`: the parity test and its self-check, and the unit tests with `debug_assertions` off, against that target's build. Those steps are known to pass on Linux glibc only. **A leg that fails its gate doesn't ship, and the build task proves every leg, macOS arm64, macOS x86_64 and musl, in a dry run before the first real run.**
   - It joins the binaries into one set, writes `SHA256SUMS`, and attests build provenance for each binary with GitHub's attestation action (pinned by commit SHA, like every third-party action).
   - On a real run (`dry_run` false) it creates a **draft** GitHub Release `v<version>` at the commit the run built. A dry run only uploads the binaries as workflow artifacts. It fails if a release or a tag `v<version>` already exists, draft or not, so a stale draft is never reused with different assets: the maintainer deletes the old draft first, on purpose.
   - **A draft is not public and creates no tag. The maintainer publishes it from the Releases page, and that click creates the tag.** That is two deliberate steps, the run and the publish.
   - The build jobs get `contents: read` only. Only the last job gets `contents: write` and the attestation permissions.
3. **Assets.** An asset is a bare executable named `logseq-mcp-server-<version>-<target triple>`, with `.exe` when Windows joins. It is not an archive, so the launcher needs no extraction and a user can download the one file they need. `SHA256SUMS` lists every asset in `sha256sum` format. **Licence notices ship as assets, not inside the binary:** the release carries `LICENSE` and `THIRD-PARTY-NOTICES.txt` (some dependencies are MPL-2.0 or Unicode-3.0, not MIT), the launcher downloads both into the cache directory beside the binary and checks them against `SHA256SUMS`, and a user who downloads by hand finds them on the release page. The generator of the notices is a new tool that CLAUDE.md says to vet first. #418 picks it, and a release doesn't go out without the notices. Printing them from the server (a flag) is not chosen: it adds to a stdio server's surface for a text the release can carry.
4. **Integrity.** The launcher downloads the asset and `SHA256SUMS` from the release of its own version and refuses to run a file whose SHA-256 isn't the listed one. It never falls back to an unverified binary. `SHA256SUMS` catches a truncated or corrupted download, and the attestation (`gh attestation verify`) ties a binary to the workflow run and commit for anyone who wants that check. Neither protects against a compromised release account, since the checksum file sits beside the binary. Anything stronger, such as hashes recorded in the repository at the tagged commit, is a later decision.
5. **Signing.** The first release has no Developer ID signature and no notarization. macOS arm64 binaries carry the linker's ad-hoc signature. The launcher downloads with `curl`, which doesn't set the quarantine attribute that makes Gatekeeper block an unsigned binary. A binary downloaded by hand through a browser is quarantined, and the README says to clear it with `xattr -d com.apple.quarantine <file>`. Whether this holds on a clean machine is a step of the first-release check (below), not an assumption. Whether to enrol in Apple's developer program is the maintainer's decision, and signing and notarization are additive when they land.
6. **The launcher.** One tracked `*.sh` file in the repository (its path and name are #419's), POSIX `sh`, so the ShellCheck job in `ci.yml` (#381) lints it. It needs `uname`, `curl`, and `shasum` or `sha256sum`, which macOS ships and most Linux installs have, and **no Node**. It:
   - Maps `uname -s` and `uname -m` to a target, and reads its version from the repository (the version test holds every copy equal).
   - Looks for `<user cache dir>/logseq-mcp-server/<version>/<asset>`. If it is missing, it downloads the asset, `SHA256SUMS`, `LICENSE` and the notices from `https://github.com/eborden/logseq-mcp-server/releases/download/v<version>/`, verifies the hash, sets the executable bit, and moves the file into place with an atomic `mv` from a temporary name, so a failed or concurrent download never leaves a half-written binary where the next start would run it.
   - Ends in `exec` of the binary, so the launcher leaves no process, and signals and exit codes are the binary's own.
   - Writes every message of its own to stderr and nothing to stdout, which is the MCP channel ([ADR-0004 (stderr-only-logging)](0004-stderr-only-logging.md)). It holds no token or config value, and never prints one ([ADR-0003 (no-secrets-in-source)](0003-no-secrets-in-source.md)).
   - Honors the proxy variables `curl` reads (`HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`).
   - Takes two overrides for the user's own machine. `LOGSEQ_MCP_BINARY`, an absolute path, skips the download and runs that binary, for offline use. `LOGSEQ_MCP_RELEASE_BASE_URL` replaces the download base (everything up to the file name), and accepts a `file://` directory, for tests and for the pre-publish check below. Verification against `SHA256SUMS` from the same base still runs.
   - On an unsupported platform, a missing release, a failed download (offline, or a proxy it can't pass), a missing `curl` or hash tool, or a checksum mismatch, exits non-zero with a message that names the cause and the manual route (download the binary, check it against `SHA256SUMS`, set `LOGSEQ_MCP_BINARY`).

   A Windows launcher is a second file, in PowerShell or Node, written when Windows joins. That cost is accepted now because Windows is deferred.
7. **The plugin** starts the launcher: `.claude-plugin/plugin.json` runs it through `${CLAUDE_PLUGIN_ROOT}`. The binary isn't in git, and a marketplace install of any commit works as soon as the release of that commit's version is published. No npm publish is involved. Node is not required of a plugin user, which suits Claude Code's native installs.
8. **npm.** There is no npm channel in the first release, and `package.json` is repository tooling: #419 removes `dist`, `main`, the `build` script and `prepublishOnly`, drops `bin` and `files`, and sets `private: true` so a publish by accident fails. Whether to publish to npm later is the maintainer's choice, to be made against these facts:
   - The unscoped name is taken, so the name has to change. We recommend a **scoped** name, `@<scope>/logseq-mcp-server`, because a scope can't collide with anyone's unscoped package. **The maintainer picks the scope, creates it (a user or organization they control) and confirms the name is available and theirs.** No session claims, reserves or publishes a name.
   - A different unscoped name is possible if one is free, at the cost of a name nobody searching for "logseq" finds more easily, and the same duty to confirm it.
   - If an npm package is ever published, it carries the same shell launcher, so it works on macOS and Linux, and a new manual workflow publishes it under ADR-0017's rules (restated in Decision 10). The `npx` one-liner is the thing the first release gives up. A user of a host without plugins (not Claude Code) clones the repository or downloads the binary, and points the host's `command` at the launcher or the binary.
9. **One version.** The number in `rust/Cargo.toml` is the version the binary reports as `serverInfo.version`. It, `package.json`, `.claude-plugin/plugin.json` and the marketplace entry are equal, held by the version test that already exists. The first release is `1.0.0`, which is what all four say today. No `1.0.0` was published from this repository, so the number isn't reused. A release is cut by a PR that bumps the four together, then a run of `release.yml` at that version. Versions follow semver, with the tool contract's additive-only rule ([BR-0004 (additive-tool-contracts)](../business-rules/0004-additive-tool-contracts.md)) deciding minor against major. The launcher fetches exactly the version its repository says, never "latest", so the launcher and the binary can't drift apart.
10. **The rule from ADR-0017, carried over.** Publishing of any kind is a manual workflow that runs only on `workflow_dispatch`, only from `main`, with a `dry_run` input that defaults to true, with third-party actions pinned by commit SHA, started by the maintainer from the Actions tab. The working rule that nothing is published, tagged or released from a session stays in CLAUDE.md and applies to every step here.
11. **ADR-0017 is superseded by this ADR**, because its Decision names the TypeScript build and `npm publish` of `dist`, and this ADR replaces what is published and how, while keeping who starts it. Removing or rewriting its guards (`tests/guards/package-metadata.test.ts` lines on `prepublishOnly` and `dist`, and the `publish.yml` guards in `tests/guards/adr-workflow-guards.test.ts`) is removing enforcement. **The maintainer's OK to accept this ADR is also the OK for that removal and for ADR-0017's supersession**, which is made in this PR, and the removal itself happens in #419's PR, which cites the OK. ADR-0018's layout and skills decisions stand, and only the server command changes, so it isn't superseded.
12. **The first release is a manual step by the maintainer**, in this order, none of it from a session:
    1. The cutover is on `main` (#354), and #418 and #419 are merged.
    2. The maintainer runs `release.yml` with `dry_run` on, reads the artifacts, and confirms every gate leg was green.
    3. The maintainer runs it with `dry_run` off. It creates a draft release.
    4. **Pre-publish check.** Draft assets aren't downloadable without authentication, so the launcher's default URL can't be tried before the release is public. The maintainer downloads the draft's assets with the authenticated `gh release download` into an empty directory, and runs the plugin's launcher on a clean macOS machine and a clean Linux machine with `LOGSEQ_MCP_RELEASE_BASE_URL` set to that directory as a `file://` URL, then calls one tool. That exercises the download through `curl`, the checksum check, the cache, the `exec` and the plugin command. A draft asset saved through the browser, while signed in, is also run by hand to see what Gatekeeper does with a quarantined binary. What this can't check is the default download URL and anonymous access. A unit test pins the URL pattern, and the next step is the real check.
    5. The maintainer publishes the release, which creates the tag.
    6. **Post-publish check.** On a clean machine with no override, the maintainer starts the plugin once and calls one tool. If that fails, the release isn't edited: the fix is a new patch version, `1.0.1`, cut the same way.
    7. Only if the maintainer chooses an npm channel, later, and under a name they have confirmed (Decision 8), a manual workflow publishes it with `dry_run` on, then off.

### Alternatives rejected

- **Option 2, a Node launcher shared with an npm package.** It is the one cross-platform launcher, but it keeps a Node process resident (about 34 to 35 MB measured), adds Node's start-up, makes Node a runtime requirement for every user (changing the scope ADR-0022 gives its floor, and leaving out Claude Code's native installs), and its `fetch` ignores the proxy variables. Its only advantage over option 1 is Windows, which is deferred. It is the likely shape of the Windows launcher, if that one is written in Node.
- **Option 3, per-platform npm packages with optional dependencies.** It needs a scope or organization created in the maintainer's npm account (the unscoped name is taken), one launcher package and one package per platform, each published by hand with provenance, and a Node shim at run time, with the same resident cost as option 2. The plugin would depend on an npm publish. Its upside is that the first run needs no network and the registry vouches for the files. Not ruled out later, as an additive channel.
- **Option 4, a binary-only plugin.** It needs no Node and no network at run time. But committed binaries (about 3 to 4 MB each, times targets, times releases) stay in git history for good, or a CI job has to write to a release branch, which is a push no session may make. It still needs a platform picker, and the plugin at `main` would hold no binary. Revisit this if Claude Code adds platform-specific plugin files or a download step of its own.
- **Option 5, `cargo install` only.** It needs a Rust toolchain (1.88, pinned) and a build of a few minutes, and it is a poor fit for a plugin. It stays as a documented path for developers.
- **`curl | sh` of a remote script.** That pipes unreviewed remote code into a shell. A checked-in launcher that fetches a pinned, verified binary is a different thing and is what option 1 is.
- **A release tool such as `cargo-dist`.** It is a new tool to vet for a three-job matrix. A hand-written workflow is easier to read against ADR-0017's rules. Revisit if the matrix grows.
- **Building on every merge or tag.** That publishes without a deliberate choice at that moment, which ADR-0017 rejected.
- **A fallback to the TypeScript server for one release.** The Go on #349 retired it (#356), and nothing in this decision brings it back.

## Consequences

- **The server stays about 2 MB resident, and starts in milliseconds**, because the launcher `exec`s and leaves nothing behind. The install is about 3 to 4 MB, with no Node and no `node_modules`. #419 measures the launched server with `scripts/measure-footprint.ts` and reports it.
- **The launcher needs `sh`, `curl` and a SHA-256 tool.** Minimal Linux containers may lack `curl`, and the launcher says so and names the manual route. A corporate proxy that `curl` can't pass fails the first download the same way. `LOGSEQ_MCP_BINARY` is the offline path.
- **The first run needs the network**, for a few MB from `github.com`. Later runs read the cache.
- **There is no `npx` one-liner**, and no npm package in the first release. A user outside Claude Code's plugin system clones the repository or downloads the binary by hand. The existing `npx -y logseq-mcp-server` lines in the README, `CHANGELOG.md` and the two older ADRs run another maintainer's package, which is a risk to users until #417 lands. This ADR doesn't fix that text and doesn't claim the name.
- **Windows users have no binary in the first release.** That is a real gap for LogSeq's Windows users. It is stated, so it isn't a surprise, and the route to close it is named: local time on Windows, a gate on a Windows runner, and a second launcher.
- **The launcher is shell, so it is tested through a stub server and a `file://` base**, not unit-tested like TypeScript. ShellCheck lints it, and #419 owns its tests.
- **The plugin and the release can disagree for a short time.** The marketplace entry is the repository's default branch, so a bump of the four version numbers merged before the release is published makes the plugin ask for assets that don't exist yet, and the launcher fails with the version it wanted. The release process keeps the window short: run `release.yml` right after the bump merges, and publish the draft in the same sitting. The launcher never guesses an older release.
- **macOS binaries aren't notarized.** Anyone who downloads one in a browser meets a Gatekeeper warning until they clear the quarantine attribute. The launcher path should avoid it, to be confirmed in step 12.4.
- **The release workflow can't be fully tested without making a release.** Its first dry run on GitHub is the real test, as ADR-0017 found for npm. The draft step keeps the build recoverable (a draft can be deleted). It doesn't cover the launcher's default download URL, which is checked after publish (step 12.6), and a bad release is fixed by a new version, not an edit.
- **GitHub's Intel macOS runners are on a retirement path.** `macos-15-intel` is the only runner that runs an x86_64 macOS binary natively. When it goes, that job cross-compiles from the arm64 runner and its gate runs under Rosetta or not at all. That is a later decision, and a reason to check before relying on the runner name.
- **ADR-0017's guards go with its supersession.** The version test and the repository-wide rule "no workflow runs `npm publish`" stay (the latter as a guard written for the new workflows, in #418). The maintainer's OK to this ADR covers the rest (Decision 11).
- **More to maintain**: a launcher, a second workflow, checksums and attestations, and a licence-notice step. The workflow's cost is about 2 to 7 minutes of job time per target on a cold cache (#304), paid only on a release.
