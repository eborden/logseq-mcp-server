# Ratchet per-file mutation scores on the Rust crate with cargo-mutants

## Context

[ADR-0026 (mutation-testing-ratchet)](0026-mutation-testing-ratchet.md) ratchets per-file mutation scores on the TypeScript unit suite with Stryker, and [ADR-0027 (cap-mutation-cache-miss-set)](0027-cap-mutation-cache-miss-set.md) to [ADR-0030 (nightly-check-resets-a-stale-mutation-cache)](0030-nightly-check-resets-a-stale-mutation-cache.md) tuned its CI job: a cap on the cache-miss set, then a mutant budget, then a plan taken from the PR's own diff, then a nightly reset of a stale cache. The Rust crate (`rust/`, [ADR-0025 (rust-implementation-alongside-typescript)](0025-rust-implementation-alongside-typescript.md)) has no mutation testing. #349 decided Go on 2026-10-08, so Rust becomes the only server on `feature/rust-spike` and #356 retires the TypeScript server and the Stryker job with it. The Rust port's safety net is its tests (unit tests, the parity cases, and the integration suite run against it on the fixture instance, #352), and nothing measures how strong they are. Proposed in #351. The issue's other option, relying on the parity cases and unit tests alone, costs nothing and measures nothing.

**Nothing in this ADR was run locally.** The maintainer's rule is no heavy local CPU, so there is no spike like ADR-0026's. The numbers below come from the tool's documentation, crates.io, and the CI step timings of the Rust job on 2026-10-08 (warm cache: debug build about 7 s, `cargo test` about 13 s). Every constant is set from a CI measurement in #364, and a measurement that contradicts an assumption here stops that work (foundations section 0).

### How cargo-mutants differs from Stryker

These facts decide what carries over from ADR-0026 to ADR-0030. The first four are from the tool's documentation.

- **It mutates function bodies and operators, not literals.** It replaces a function's body with a guessed value, swaps binary operators, deletes unary operators, deletes match arms (when a wildcard arm exists), sets match guards to `true` and `false`, and deletes struct-literal fields that have a base expression. It doesn't mutate string literals or constants. The 301 string-literal survivors that ADR-0026 had to reason about, the `StringLiteral` mutator and `ignoreStatic` have no counterpart.
- **An outcome is caught, missed, unviable (it doesn't compile) or timeout.** There is no "no coverage" status: uncovered code is a missed mutant. Exit code 2 means some mutant was missed and 3 means a timeout. Neither is a broken run. 4 means the unmutated tests already fail, 5 and 6 mean `--in-diff` was given a diff that doesn't match the tree or isn't one, and 70 is an internal error.
- **It has no incremental file.** `--iterate` skips mutants caught in an earlier run, and its documentation calls it "a heuristic" that assumes new changes won't reduce coverage. A gate can't rest on that, since a deleted or weakened test is exactly what a ratchet is for. So there is no results cache, which removes the blind-spot inputs, the cache keys and the restore and save rules of ADR-0026 and ADR-0028, and the stale-cache problem that ADR-0029 and ADR-0030 worked around.
- **`--in-diff <diff>` mutates only what overlaps the diff's changed lines in source under test**, and a diff that only touches tests generates nothing. Its documentation warns that an edit in one place can leave another place or file poorly tested.
- **Each mutant costs a rebuild and a test run**, where Stryker's `perTest` coverage runs a few tests per mutant in one process. By the step timings above a mutant is on the order of 20 s, and the crate has about 1,300 `fn` items with their tests, so a cold run over the whole crate is thousands of mutants: hours, likely past one job's 6-hour limit. That is an estimate. A PR job of 20 minutes holds on the order of a hundred mutants at `--jobs 2`. This is the main reason the PR job below works on the PR's changed code and not on whole files.
- **`--jobs` is a different knob from Stryker's `concurrency`.** Each job has its own target directory, `cargo build` and `cargo test` already use many threads, and the documentation advises starting at 2 or 3 and warns that a non-hermetic suite flakes under parallelism. Several of the crate's integration tests bind a local port for a stub LogSeq.

## Decision

We adopt mutation testing on the Rust crate with `cargo-mutants`, and a per-file ratchet in CI. It is introduced in two steps, as ADR-0026 did: an informational job first, then a committed baseline and enforcement (both in #364), with a three-run flakiness experiment in between.

**Tool and scope.**
- `cargo-mutants` 27.1.0, installed in CI only, pinned to an exact version. An upgrade can change the mutator set and so every score, so it is its own PR and it re-baselines.
- Its configuration is `rust/.cargo/mutants.toml`. The mutated scope is every file under `rust/src` that has mutants, with no exclusions to start. ADR-0026 left out type declarations, schema declarations, wiring and text constants because Stryker mutated them as noise. `cargo-mutants` doesn't mutate any of those. Later changes to the scope (`examine_globs`, `exclude_globs`) or to the skipped tests (`additional_cargo_test_args`) are treated like lowering a score (below). An ignore is not a scope change (below).
- The tests are whatever `cargo test --locked` runs on the debug profile, which is also the only profile where the test clock `LOGSEQ_MCP_NOW` works. The TypeScript parity harness is not part of a mutant's run: it needs Node and a build outside cargo, and #356 turns the recorded parity results into golden tests that `cargo test` then runs. Tests that scan source text or check a policy, not behaviour, may be skipped with `additional_cargo_test_args`, by the same test as ADR-0026: only if measurement shows they cost time or flake, and each one is named in the config.
- The score is caught and timed-out mutants over caught, timed-out and missed ones. Unviable mutants count for nothing, and ignored ones are out of both numerator and denominator. A timeout counts as caught, as in ADR-0026 (`cargo-mutants` times a mutant out at 5 times the baseline test time, 20 s at least).

**Baseline.**
- `rust/mutation-baseline.json`, a separate file from the TypeScript `mutation-baseline.json`, so both ratchets coexist and #356 can delete the old one without touching this one. It holds the tool version and, per file, `"rust/src/x.rs": { "score": 91.3, "ignores": 2 }`, one line per file in sorted order.
- Carried over from ADR-0026 unchanged: raising is by hand from the full run's report (or the lower of two runs) and never from CI, and **the raise keeps ADR-0026's margin**: the score is rounded down to a whole point and then reduced by the file's observed run-to-run spread in mutants, converted to points (a one-mutant move in a small file is several points, so a raise to the exact measured number would turn a full run red on noise, and `--jobs 2` with port-binding tests is no less flaky than Stryker was); lowering is a decision that needs the `mutation-baseline-change` label and the maintainer's OK, as does an edit to the scope or the skipped tests; a baseline entry with no row in the report, and a file with mutants and no entry, both fail; a new file must reach 80% and gets its entry in the same PR.
- **Ignores keep ADR-0026's split: a written reason and an `ignores` bump, no label.** An ignore is an `exclude_re` entry in `rust/.cargo/mutants.toml`, preceded by a `# reason:` comment, and the PR that adds it raises the file's `ignores` in `rust/mutation-baseline.json`, so the growth shows in the diff and in review, as an inline `Stryker disable` did. The check reads the `exclude_re` entries apart from the scope keys, so an ignore doesn't need the label, and an equivalent mutant on a new line is cleared by the author with a reviewed reason, not by the maintainer. `ignores` is the number of mutants the entries remove from the file, found by listing mutants with and without them (`--list` parses the source and builds nothing). An entry that matches no mutant, as after a rename, fails the check, and a file whose mutants reappear fails by score, so a stale ignore is loud.
- **An `exclude_re` pattern matches the function and the mutation text, never a line number or column**, so an edit above it doesn't stale it. The check rejects a pattern that carries a `file:line` form. #364 confirms what name the tool matches the regex against.
- **The in-source attribute is the fallback, not the choice.** `#[cfg_attr(test, mutants::skip)]` is visible at the site, which the tool's documentation prefers. As far as we know it needs the small `mutants` crate only as a dev-dependency, and the tool reads the attribute from the syntax tree, so nothing would reach the shipped binary. #364 confirms that (a build of the release binary with the crate absent from its normal dependencies), and if `exclude_re` proves brittle the ADR is amended to switch, after vetting that dev-dependency.

**Where it runs.**
- **Quiet by construction.** One CI job per run, never a shard matrix. `--jobs` at most 2 (`MUTANT_JOBS`, set from the first measurement, 1 if load makes timeouts). A superseded PR run is cancelled. There is no push trigger, because there is no results cache to save and a PR run already tests the merge with its base. Nobody runs `cargo mutants` on a developer machine, agents included: its only local use is `--list`. A score for one file on demand is a labelled PR run (below).
- **Results cache versus dependency cache.** There is no *results* cache (above). A *dependency-build* cache is allowed and needed: it holds compiled dependencies and no mutant outcomes, so it can't weaken the gate. `rust.yml` saves one on a push to `feature/rust-spike` (its `Swatinem/rust-cache` key), and the mutation workflows restore it through the same shared key and never save, so a PR run can't poison it and no PR builds dependencies cold. #364 adds the shared key to `rust.yml` (which is why it waits for #356, the other editor of that file) and measures what the job's overhead costs cold and warm: the tool install, the baseline build and test run that `cargo-mutants` always does first, and whether its scratch copies of the tree can reuse restored build output.
- **The PR job** is its own workflow, `.github/workflows/rust-mutation.yml`, on `pull_request` for `rust/**` and the mutation workflow files. The plan and ratchet package must live under `rust/` (outside `rust/src`), so the one path filter covers the code that gates. It is not a job in `rust.yml`, which also triggers on parity inputs that don't change a mutation score and keeps the Rust build job's concurrency and timeout apart from this one's. `timeout-minutes: 20` to start. The existing `ci.yml` and its guards are untouched.
- **The diff base is exact.** A `pull_request` run checks out the merge commit, and `BASE_SHA` is that commit's first parent (`HEAD^1`), not `github.event.pull_request.base.sha`, which can be older once the base branch has moved and then gives a diff that doesn't match the tree (exit 5) or lands mutants on the wrong lines. The one `BASE_SHA` is shared by the plan, `--in-diff` and the ratchet, as ADR-0029 pinned one base. #364 tests it with a base that moved.
- **The plan comes from the PR's own diff** (ADR-0029), classified by region, not by path, in three groups, each sorted by path:
  1. **Changed sources**, mutated with `--in-diff`: only the mutants overlapping the PR's changed lines outside any `#[cfg(test)]` item. A new file is all changed lines, so it is measured whole.
  2. **Edited or deleted tests.** 93 `#[cfg(test)]` modules live inside `rust/src/*.rs`, so a unit test sits in the file whose code it tests, and the tool makes no mutants from test code. A change inside a file's own `#[cfg(test)]` item therefore maps to that file, which is **mutated whole with `--file`** (it subsumes the file's group 1 mutants), so a PR that weakens or deletes a unit test is checked on the PR, as ADR-0026 promised. A test under `rust/tests/` has no such mapping (no import graph the job can read): it is named in the summary and left to the next full run, as ADR-0029 left a changed test's imports. A test the PR adds is ignored, since a new test can only add kills.
  3. **Changed baseline entries**, mutated whole with `--file`, so a raise is checked against the whole file.
- **The gate.** For group 1, the score of the mutants in the changed code must be at least the file's baseline entry, or 80% and a new entry for a new file. For groups 2 and 3, the whole-file score must be at least the entry. A file below it is re-run once from a fresh directory, and the check fails only if it is still below. **An empty plan passes** (nothing was mutated, so nothing is below a baseline), **but the summary says so in words and doesn't report a pass of any file.**
- **The budget** (ADR-0028). The plan counts mutants exactly with `cargo mutants --list` over the same selection, so there is no cached count and no `FALLBACK_MUTANTS`. `MUTANT_BUDGET` is the timeout, less the job's overhead (the install, the dependency restore, the baseline build and test run), a spare and **a reserve for the one re-run** (the mutants of the largest selected file), times `MUTANT_JOBS`, over the slowest seconds per mutant measured. A re-run that can't finish in the time left is named as unverified, and for a changed source that counts as left out. The arithmetic lives in a comment on the constant. The run walks the groups in the order above and takes each file whose mutants still fit (first-fit). A file that doesn't fit is skipped and the walk goes on. Everything left out is named, with its group, in the job summary and an annotation.
- **A changed source left out fails the ratchet** until a **proof run** has measured it (ADR-0028). A left-out baseline entry, or a `rust/tests/` edit, is a warning only, covered by the full run (ADR-0029), so a re-baseline goes green. A proof run is a run of `rust-mutation-full.yml` triggered by the `mutation-proof` label on the PR (below). It checks out the same merge commit, runs the PR's own plan for just the left-out changed sources with the long timeout, and **applies the same gate with the same `BASE_SHA`**, so a large change is held to the same standard as a small one. Its artifact, `rust-mutation-proof-<head sha>`, lists the files it measured. The ratchet accepts a proof under ADR-0028's rules, which carry over: the run **succeeded**, it is a run of **`rust-mutation-full.yml`** (an artifact doesn't say which workflow made it), the artifact **hasn't expired**, and its name is built from the PR's head commit. With several such artifacts for one head commit (a label applied again), **the newest counts**. It must list every left-out changed source. The look-up is the same Actions API call, with `actions: read` and nothing else.

**Full runs, by label now and by schedule later.**
- `schedule` and `workflow_dispatch` only run for a workflow file on the default branch, and `main` is frozen until the cutover merge (#354, #122). So **until `rust-mutation-full.yml` is on `main`, it is triggered by a label on a `pull_request`**, which GitHub runs from the PR's merge commit and so works on `feature/rust-spike`. Two labels, applied only by someone with write access: `mutation-proof` (the proof run above) and `mutation-full` (a full run of the whole crate, for the three-run flakiness experiment, an on-demand score for a file the PR touches, and the backstop below). A run is tied to the PR's head commit, and its artifact lists the files it covered. The workflow declares `schedule` and `workflow_dispatch` from the start, so they begin to work the day it reaches `main`, and adding the schedule (a cron on `main`, one slice a night) is a later step then. Until then the backstop runs when the maintainer or the team lead labels a PR on a regular cadence. That is a manual duty, and without it a weakened `rust/tests/` test is unseen.
- A full run mutates whole files, uploads its report and fails when a file is below its baseline. It never blocks a PR, and it is the backstop for what the PR job can't see: a weakened `rust/tests/` test, an edit that weakens another region (the `--in-diff` caveat), and a score that moved because of load.
- **Slices.** If the measured cold run doesn't fit one job, a full run is split into `FULL_RUN_SLICES` slices of whole files balanced by their mutant counts, one job per slice, chained with `needs` so they never overlap. Once scheduled, one slice runs a night, so every file is measured at least once a week.
- **ADR-0030's nightly check does not carry over.** It resets a stale incremental cache. With no results cache there is nothing to go stale and nothing to dispatch: the schedule, when it exists, is a plain cron. The `RECENT_RUN_HOURS` guard, the caches API read and the fail-closed rules have no counterpart.

**Flakiness** (carried from ADR-0026). Before the check enforces anything, the full run is done three times, one after another with nothing else running, against one commit (by label on one PR, removing and re-applying it). The per-file spread, in mutants and not points, sets the tolerance (strict if every file is within one mutant), and the initial baseline is the lowest of the three, rounded down by the margin above. The tolerance applies in mutants to the changed-code gate as well as to whole files: a file may have that many more missed mutants than its entry allows before the gate fails. A tolerance other than strict amends this ADR, which needs the maintainer's OK. The risk to watch is specific to this tool: two mutants in flight run the crate's port-binding tests at once, and a timeout caused by load counts as caught.

**Relationship to ADR-0026 to ADR-0030.** This ADR doesn't supersede them yet. Superseding records a reversal, and they are not reversed: while the TypeScript server exists they bind its Stryker job, and `src/mutation-ci.test.ts` and the workflows still enforce them. [ADR-0025 (rust-implementation-alongside-typescript)](0025-rust-implementation-alongside-typescript.md) is itself superseded by [ADR-0031 (second-implementation-matches-tool-list-by-meaning)](0031-second-implementation-matches-tool-list-by-meaning.md), which calls itself the live record of all four of ADR-0025's decisions, so the rule here is ADR-0031's restatement of Decision 3. That rule has two branches: an ADR whose Decision is about the TypeScript toolchain applies to TypeScript only and its Rust equivalent gets its own ADR, and an ADR about how we work binds every implementation by intent. ADR-0026 to ADR-0030 are mostly the first (Stryker, vitest, `scripts/*.ts`), but the per-file ratchet they describe also reads as the second. **So this ADR is a deliberate departure from them for Rust at these points, not only a scope reading**: the PR gate measures the changed code and not the whole-file ratio; a PR doesn't compare a whole file's score except for a changed baseline entry or an edited in-file test; a weakened `rust/tests/` test is left to the full run; and a left-out changed source is proved by a label-triggered run, not by a scheduled one. The maintainer's OK on this PR covers those points.

ADR-0026 to ADR-0028 are already superseded, so only ADR-0029 and ADR-0030 are in force. **#356 retires them** in the PR that deletes the Stryker job and its scripts, and follows the README's rule for citing a file that has since been deleted wherever their enforcement lines name one. Removing enforcement needs the maintainer's OK there, as #356 already notes. The maintainer decided the statuses (2026-10-08, recorded on #365): in that PR, ADR-0029 becomes `superseded by 0033-rust-mutation-testing-ratchet`, since this ADR is its replacement for the crate that remains (the plan from the diff, the budget, the left-out rule), and ADR-0030 becomes `deprecated`, since it has no counterpart here. Those are status-only edits made by #356, not by this PR.

## Consequences

- The Rust crate gets a number per file for how well its tests catch changes, and a list of which changes they miss, before the TypeScript ratchet goes away. CI gains a PR job of up to 20 minutes that runs beside the build job, and full runs of hours.
- A PR that adds or changes Rust code must test that code at least as well as its file's baseline. It is stricter on new code than ADR-0026's whole-file ratio, and blind to the rest of the file until a full run, except when the PR edits that file's own test module (then the whole file is mutated). A PR that weakens a `rust/tests/` test can merge and be caught up to a week later (or a slice cycle). ADR-0029 accepted that for tests, and this ADR accepts it for the same reason.
- **Small diffs make the gate "no misses" in practice.** A typical diff has a handful of mutants, so against a 91% entry a 4-mutant diff fails on any single miss (75%), and below about 11 mutants any miss fails. That is intended. The measured tolerance (Flakiness) is the only slack, in mutants. An equivalent mutant on a new line is cleared by an ignore with a written reason and an `ignores` bump, which a reviewer sees, and not by the maintainer.
- The PR job doesn't compare the whole-file score, except for a changed baseline entry or an edited in-file test module. A file's score can therefore fall below its entry by a merge, and the failure shows on a full run, not on the PR.
- A changed source that exceeds the budget fails until a proof run (by label). With the budget near a hundred mutants that could be common, which is the situation ADR-0029 described for the TypeScript job (the weekly run became a step of almost every PR). If the first measurement shows it, #364 stops and comments, and the fix is a decision, not a constant: a smaller `--in-diff` selection, or a larger job.
- Full runs are by label until the workflow reaches `main`, so the backstop is a manual duty until a schedule can exist. The label path needs write access and a PR to hang on.
- The plan and ratchet are a new Cargo package under `rust/`, outside `rust/src` and the server's dependency tree. They can't stay TypeScript, whose tests live in `src/` and are removed by #356, and Node is in the Rust job today only for the parity harness. They add a small package to maintain and a lockfile of their own.
- There is no results cache, so a re-run recomputes what it measured before. That is the cost of a sound gate, and it also removes a class of failure (a stale or poisoned cache). The dependency-build cache has no results in it.
- `cargo-mutants` mutates no literals and no constants, so model-facing prose and text constants are not measured by it. The golden and parity tests are what pin them.
- The tool adds nothing to the shipped binary, and no dependency to `Cargo.toml`.
- Until #364's second PR lands there is no gate, and this ADR's enforcement is a promise.
